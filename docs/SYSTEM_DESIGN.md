# Climate & Nature Navigator: System Design (the plan we build)

> Team design by Ashutosh, 6 Nov 2026, converted from the PDF. **This is the decided plan.** Where other docs disagree, this file and `docs/CONTRACTS.md` win, and `AGENTS.md` rules still apply.

## Goal and scope

We build one traceable decision system on three tracks:
- **A:** clean data → 2025 inventory.
- **C:** weather → yield risk → €.
- **E:** a copilot that answers with evidence.

We skip B and D except for one slide each.

**The jury grades:** usefulness 30 %, sound reasoning 25 %, traceability and expert review 25 %, reliability (auto-scores) 10 %, technical quality 10 %. Auto-scores only prove we are right; the win comes from decisions, reasoning and the audit trail.

**One rule above all: deterministic code computes every number.** The LLM only classifies, explains, retrieves and phrases. No number is ever generated by a model.

**Headline story:** the current farm calculator assumes mineral soil and misses drained peat (29 t CO2/ha/yr). We find it, correct it with expert approval, and show what climate change costs the pea supply in €.

| Track | Tasks we submit | Auto-scored | Priority |
|---|---|---|---|
| A Data → inventory | A1 issues CSV, A2 inventory CSV | yes | 1 (backbone) |
| C Climate risk | C1 yields CSV, C2 risk CSV, C3 € analysis | C1, C2 | 2 |
| E Copilot | E answers CSV + live chat | numeric part | 3 (thin, built last) |
| B Pathways | one slide: the peat effect on FLAG | no | stretch |
| D Nature | one map layer if time | D1 | stretch |

## Architecture

- **A and C run in parallel from the first hour.** A's cleaned farm survey is their only hand-off.
- **Everything downstream reads approved results** with their lineage.

### Shared data layer and the "number + trail" contract

Every module reads the same loaded tables and writes results in one format, so A and C can build in parallel and E can read both. **Agree on this in hour one; it is the only hard dependency between people.**

- **Storage:** one DuckDB file (`navigator.duckdb`) plus Parquet. Loaders reuse the pack's `tools/ccn_tools/io.py`.
- **Naming:** raw tables are loaded untouched as `raw_*`; cleaned versions are `clean_*`.
- **Four shared tables:** `issues`, `corrections`, `results` and `lineage`. Exact columns are in [CONTRACTS.md](CONTRACTS.md).
- **Status values:**
  - issues go `proposed` → `approved` / `rejected`;
  - results go `draft` → `approved` → `published`.
  - Nothing reaches the UI or a submission CSV as final unless it is approved.
- **Record keys** use the official A1 format everywhere (`erp:{doc_no}:{line_no}`, `farm_survey:{survey_id}`, `pcf:{supplier}:{material}:{year}`, …). The same key then works in the CSV, the lineage table and the copilot's citations.
- **A number without lineage rows is a bug.** A unit test fails the build if any published result has none.

## Track A: data-quality agent and 2025 inventory

Rules find the mistakes, the LLM handles the grey zone and the explanations, a human approves, and the organisers' reference calculator turns the clean data into the inventory.

1. **Normalise.** Load the raw feeds and parse units, currencies, dates and the PACT JSON files into one tidy shape. Nothing is changed yet.
2. **Detectors** (deterministic, one function per issue type). Each returns candidate issues with a `rule_id` and evidence:
   - **Price per kg vs the material's median** → `unit_error`, `decimal_shift`, `currency_error`, `material_mismatch`.
   - **Exact-match keys** → `duplicate_record`. For travel: same traveller, date, route, distance and nights; flag the later row.
   - **Monthly series gaps and robust z-scores** → `missing_record`, `meter_spike`. Build the seasonal profile first, so real peaks pass.
   - **Cross-file checks:**
     - `certificate_mismatch`: the GoO log vs the registry;
     - `missing_leg`: a sea import without both road and sea legs;
     - `area_mismatch`: the survey vs the parcels;
     - `total_mismatch`: the draft report vs the sums.
   - **Soil map** → `soil_misreport` when ≥ 30 % of a farm's crop area is organic but the survey says mineral.
   - **Lookups** → `wrong_gas_code` (gas vs the site's system), `pcf_unit_error`, `pcf_stale_period`, `coordinate_swap`, `outlier_implausible`.
3. **Allow-list for legitimate oddities.** Credit notes (movement 122), vessel lots in tonnes (`uom = TO`), seasonal peaks and real ammonia systems are suppressed with a logged "checked, legitimate" note. These protect precision.
4. **LLM triage (grey zone only).** For candidates between two thresholds, the LLM sees the record, its neighbours and the rule evidence. It returns issue_type, confidence and a one-line explanation as structured JSON. **It never edits data.**
5. **Expert review.** Candidates go to the review queue. Accepted ones become `corrections` rows with the old value, new value and reason.
6. **Inventory.** Apply the approved corrections, build the canonical tables from `METHODOLOGY.md`, and call `reference_calculator.py`. Write every category line to `results`, with lineage down to record keys and factor ids.

**Validation loop:**
- Run steps 1–6 on 2023 and 2024, and score with `score.py` against the public labels and inventories.
- Tune the thresholds, then run 2025.
- Targets: beat the 52 A1 baseline and the ~25 A2 baseline by a wide margin.

**Outputs:**
- `A1_issues_submission.csv` and `A2_inventory_2025_submission.csv`.
- The corrections log.
- A 2025 farm footprint with organic soils, shown next to `current_calculator_footprints.csv` (the peat reveal).

## Track C: weather → yield → € risk

One yield model, trained once on cleaned farm history, run three ways: C1 (2027–31 by field), C2 (2041–60 by region × crop × SSP) and C3 (€ and actions).

1. **Training labels.** Farm × crop × year yields for 2012–2026:
   - from the cleaned Finnish survey, with A's corrections applied;
   - from the Swedish Foodhills file (parse `;` and decimal commas; yield = delivered ÷ area).

   Cross-check against ERP deliveries, and drop or down-weight conflicts. Missing survey years stay missing, never zero.
2. **Field → weather link.** Link each parcel to its nearest climate grid cell.
3. **Features from daily weather, mirroring the simulator.**
   - **Per field × year:**
     - sowing date (the first 5-day window above the crop threshold);
     - growth stages by degree-days above 5 °C;
     - a soil-water bucket by soil class, reset on 1 April.
   - **Stress features built on those:**
     - drought stress by stage;
     - hot days at flowering;
     - heavy rain after sowing × clay;
     - rain before harvest;
     - season length;
     - blight weather (potato: warm and wet Jul–Aug);
     - beetle weather (turnip rape: warm May).
   - **Static features:** soil, clay %, slope, drainage, irrigation, N, sprays, organic, previous crop, year trend.
4. **Model.** Per crop: a log(yield) regression with a per-farm effect (the hidden farmer skill) and interactions (irrigation × drought, clay × waterlogging).
   - Compare it with LightGBM (or sklearn gradient boosting) on the same features, and keep the better one or average them.
   - The labels are per farm but the predictions are per field, so aggregate field features to the farm's crop area for training.
5. **Backtest.** Train up to 2023, predict 2024–2026, and compute both C1 metrics (production MAPE by region × crop × year, and field nRMSE). **2026 is the key test:** strong Finnish peas, drought-hit Swedish peas.
6. **C1 run.** Build features for every planned field × year on the `ssp245` 2027–31 weather → `C1_yields_2027_2031_submission.csv`.
7. **C2 run with our own weather ensemble.**
   - The truth is a Monte Carlo, but we get only one weather realisation per SSP.
   - So we build many futures by applying the `climate_change_signals.csv` deltas to resampled 1991–2020 years.
   - Run the model on the 2025 parcel mix with current irrigation.
   - Report the mean yield change and `p_bad_year` (< 80 % of the 1991–2020 mean) per region × crop × SSP.
8. **C3 € risk.**
   - The cost: shortfall t × contract price × replacement premium, plus the emissions of replacement imports (factors from A).
   - **Adaptation value:** irrigation on drought-exposed fields, earlier sowing, and two-region sourcing (quantify the 2026 hedge). Each comes with €, t CO2e and an owner.

**Outputs:**
- The two CSVs.
- A C3 table of € at risk and actions.
- Per-feature effects for the jury, e.g. "each hot day at pea flowering costs X %".

## Track E: evidence copilot

An agent with two tools that only reports what the tools return. Every answer carries its evidence.

| Tool | Answers | How |
|---|---|---|
| `query_results` | The 21 numeric questions and any "how much" question | Parameterised SQL over `results` + `lineage` (approved rows only). Returns value, unit, status and the lineage rows |
| `search_frameworks` | The 10 rubric questions (FLAG, GoOs, EUDR, ESRS E3, LSR, SBTN) | Retrieval over `framework_digest.md`, `source_registry.csv` and the pack `docs/`. Small enough for one index, or even to fit in context. Returns passages with file and section |
| `what_if` (stretch) | "Pea supply in a 2045 drought?" | Calls C's precomputed scenario results |

**Answer rules** (in the system prompt *and* enforced in code):
- **Numbers must come from tools.** A number in the answer must equal a number a tool returned. A post-check compares them and blocks the reply if not.
- **Evidence in every answer.** Every answer ends with its evidence: record keys, file and row, or standard and section.
- **No tool result means no answer.** The reply is "not in the data", plus what would be needed.
- **Frameworks come from the pack, never from model memory.** Several rules are dated 2026.
- **Draft results are flagged.** Results still in `draft` show a "pending expert approval" badge.

**Submission:**
- A script runs every question in `E_questions.csv` through the same agent and writes `E_answers_submission.csv`.
- Check the 3 dev questions (E90–E92) first; tolerances are 3–10 %.
- E is built last and kept thin: its numeric score is earned by A being correct.

## Expert review and approval

A human approves every correction and every published number; the system only proposes. This is a quarter of the jury grade, so it is a visible feature, not a footnote.

1. **Review queue.** Each proposed issue shows the record, the rule that fired, the evidence (e.g. price/kg vs the median, the soil-map share), the LLM's explanation and the proposed fix.
2. **Decision.** Accept, reject or edit, with an optional comment. This writes `approved_by`, `approved_at` and the reason to `corrections`.
3. **Bulk accept** for high-confidence rules (exact duplicates, registry-backed GoO fixes), each still logged one by one. Grey-zone and high-impact items (soil misreports, anything moving a category by > 1 %) need individual review.
4. **Recalculate.** Approved corrections trigger a rerun, and affected `results` go back to `draft` until a reviewer publishes them.
5. **Publish.** Only `published` results feed the submission CSVs, the dashboard and the copilot.

**For the submission and the demo:**
- We pre-review the queue ourselves, acting as experts, and the full log ships in the repo as `out/corrections.csv`.
- In the demo, one correction is approved live.

**A second list, not scored:** oddities we noticed that match no issue type go to "observations for expert review". They never go into the A1 CSV, because they would cost precision.

## UI and demo flow

One **Streamlit** app with four pages plus a copilot panel. Everything reads precomputed tables, so nothing slow or flaky runs live.

| Page | Shows | Demo moment |
|---|---|---|
| Data quality | Review queue, issue counts by type, the legitimate-oddities list | Approve one soil misreport live; the total updates |
| Inventory | 2025 Scope 1, Scope 2 (location / market), Scope 3 by category; FLAG share | Click any number → records → corrections → factor → formula |
| Farm & peat | Parcel map; farm footprints with vs without organic soils | "Your calculator says X; with peat it is Y" |
| Climate risk | Yield change and bad-year odds by crop × SSP, € at risk, adaptation options | Drag the SSP slider; € and the map change |
| Copilot (side panel) | Chat with evidence chips and approval badges | A judge asks a question; the answer opens its trail |

**Demo script** (about 4 minutes, rehearsed):

| # | Beat | Time |
|---|---|---|
| 1 | Problem: the calculator assumes mineral soil | 30 s |
| 2 | Data quality: raw files in, issues found, one approved live; official scores vs baselines | 60 s |
| 3 | Click-through: a 2025 number back to its invoice line | 45 s |
| 4 | Peat reveal and the climate slider: € at risk, the two-region hedge | 60 s |
| 5 | Copilot: one live question with evidence | 30 s |
| 6 | What Apetit should do next week: 3 actions with €, t and owners | 30 s |

**The two audiences:**

## Tech stack and Microsoft mapping

We build on the fastest local stack and document a one-to-one mapping onto Apetit's Microsoft ecosystem. The brief allows this while Azure access is unconfirmed.

| Layer | Hackathon build | Apetit's stack (Fabric / Azure) |
|---|---|---|
| Storage | DuckDB + Parquet | Fabric Lakehouse (Delta tables) |
| Pipelines | Python modules, one `make all` | Fabric notebooks / Data Factory pipelines |
| Calculation | `ccn_tools` reference calculator, pandas | The same Python in Fabric notebooks |
| Yield model | scikit-learn / statsmodels, LightGBM | Azure Machine Learning |
| LLM + tools | Any frontier model via API, structured JSON output | Azure OpenAI in AI Foundry, an agent with the same tools |
| Retrieval | Local embeddings index | Azure AI Search |
| Review + UI | Streamlit | Power Apps (review) + Power BI (dashboards) |
| Copilot | Streamlit chat | A Copilot Studio agent calling the same tools |
| Audit trail | `corrections`, `lineage` tables | The same tables in the Lakehouse + Purview lineage |

- **Before writing the mapping slide,** read the pack's `docs/AZURE_FABRIC_QUICKSTART.md`.
- **If Azure credits arrive,** move only the LLM calls to Azure OpenAI; everything else stays.
- **Determinism:** fixed seeds, a pinned `requirements.txt`, and LLM calls cached by input hash, so a rerun reproduces the same CSVs.

## Team split (3 people, 3 agents)

One owner per pipeline, and one for the platform and the story.

| Person | `AGENT_LANE` | Owns | Hands off |
|---|---|---|---|
| 1 · Data | `A` | Track A: loaders, 18 detectors, allow-list, LLM triage, corrections, A2 inventory, peat numbers | Cleaned farm survey to Person 2 (first task); results + lineage to Person 3 |
| 2 · Climate | `C` | Track C: weather features, yield model, backtest, C1, C2 ensemble, C3 € risk | Results + lineage and feature effects to Person 3 |
| 3 · Platform + story | `platform` | Shared tables and the lineage writer, review app, copilot + E CSV, Microsoft mapping, slides, method note, demo | The schema to everyone (first task); acts as expert reviewer of Person 1's queue |

Person 3 reviews the corrections because they did not write the detectors, so the review is not the system grading itself. The final approvals are made by humans.

**Checkpoints (everyone syncs):**

1. **Schema agreed, baselines run.** Nobody writes results before this.
2. **First end-to-end run:** every CSV we plan to submit (A1, A2, C1, C2, E) exists and scores, even if weak. No polishing before this.
3. **Improve by score and by demo:** each person works on whatever moves their auto-score or the demo story most.
4. **Freeze:** code freeze, final CSVs, recorded demo, rehearsal, submit early.

## Risks and fallbacks

| Risk | Effect | Fallback |
|---|---|---|
| Daily-weather stage features take too long | C1 stuck at a weak model | Ship the monthly-feature model first; stage features are an upgrade, not a blocker |
| A's detectors over-flag legitimate oddities | A1 precision drops | Allow-list first; tune thresholds on 2023–24 F1 before running 2025 |
| A2 is off because one category is wrong | Large weighted loss (category 1 is 20 %) | Compare each category with the public 2023–24 truths; fix the worst line first |
| C trains on dirty survey yields | Biased model | Person 1 cleans the farm survey before anything else |
| The LLM invents a number or rule | Lost trust, zero rubric credit | Post-check: every number must match a tool result; frameworks only from the pack |
| Azure access never arrives | None for scoring | Local stack + mapping table; the jury explicitly accepts this |
| The live demo fails | Lost demo points | Precomputed tables, a recorded run, screenshots in the slides |
| Running out of time | Everything gets thinner | Cut order: D, then E's chat UI (keep the CSV script), then C3 detail. **Never cut A's audit trail** |
